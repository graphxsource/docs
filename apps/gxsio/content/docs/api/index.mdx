## Base URL

```text
https://api.graphxserver.io/
```

Every path in this reference is relative to that URL. V1 paths start with `/api`, while V2 paths start with `/v2`.

| Path in the reference | Full URL |
| --- | --- |
| `/health` | `https://api.graphxserver.io/health` |
| `/api/ProductLine/GetAllProductColors` | `https://api.graphxserver.io/api/ProductLine/GetAllProductColors` |
| `/v2/location-aliases/{id}` | `https://api.graphxserver.io/v2/location-aliases/{id}` |

## Authenticate

Send an organization API key in the `Authorization` header. Create one by following [Create and manage API keys](../api-keys/index.mdx).

```bash
curl "https://api.graphxserver.io/api/ProductMockupRequest/GetSuppliersForCompany?companyname=Acme" \
  --header "Authorization: Bearer $GXS_API_KEY"
```

The key decides which company's data you see. A request for a record that belongs to another company fails with "does not belong to your company". Load the key from your secret store and keep it out of shell history, code and logs.

Every endpoint except the three health checks needs this header. Without it, the API answers `401` with "Missing Authorization header". The schema only declares authentication on the V2 endpoints, but the V1 endpoints need it too, so this reference marks them as requiring it.

## V1 and V2

V1 copies the contract of the older GraphxServer.io API so existing integrations keep working. Its paths are PascalCase, such as `GetProductListForCustomer`, and successful responses wrap their data in a `tObject` field.

```json
{
  "tObject": [
    { "id": 1, "title": "PCNA" },
    { "id": 7, "title": "GraphXSource" }
  ]
}
```

The schema doesn't describe V1 response bodies, so the reference shows them as "Empty". Use the playground to see a real response.

V2 uses resource-style paths such as `/v2/location-aliases/{id}`. V2 includes location aliases and lifestyle image generation. If you're starting a new integration and V2 covers what you need, use V2.

Some V1 endpoints exist in the schema but aren't built yet. They answer `501` with the code `GXSIO.ENDPOINT_NOT_IMPLEMENTED`. In the development environment this includes `GetAllProductLines` and `GetGraphXServerAPIToken`.

## Errors

Errors come back as JSON problem details with a matching HTTP status.

```json
{
  "type": "https://graphxserver.io/problems/unprocessable",
  "title": "Unprocessable request",
  "status": 422,
  "detail": "A product identifier is required",
  "instance": "/api/ProductMockupRequest/GetProductPartDetails",
  "code": "GXS.UNPROCESSABLE",
  "traceId": "5c8dc4d33be2623..."
}
```

Include the `traceId` when you report a problem. It lets the API team find the request in their logs.

The schema's description says V1 returns business errors as HTTP `200`. That isn't what the development API did when this page was written. Missing parameters, unknown records and unbuilt endpoints all returned `400`, `404`, `422` and `501`. Check the status code, and don't treat every `200` as a success until the API team confirms which behavior is intended.

## Use the playground

The playground sends real requests to the production API from your browser. Paste a production API key into the authorization field. Use a test organization when trying requests. `POST`, `PATCH` and `DELETE` requests change data.

Endpoint summaries, parameter descriptions, and health-check messages are manually translated into English. API paths, parameter names, and payload fields keep their original names.

Some query parameters, such as `CustomerName` and `CompanyName`, are marked required. In testing, `GetProductListForCustomer` returned the key's own products without `CustomerName`, so the key seems to decide the company. Send these parameters anyway until the API team says they can be dropped.
